# Multilingual PII token classifier — v4.1 (shared model), v4.2 (language adapters), v4.3 (small and fast)

The same 8 PII labels as v3, in **12 languages**: English, Simplified and Traditional Chinese,
Japanese, Korean, Hindi, Arabic, Thai, Vietnamese, Malay, Indonesian and Tagalog. Context is
**wealth management**: compliance, investment, portfolio, risk and relationship-manager text.

| | **v4.1** (Model A) | **v4.2** (Model B) | **v4.3** (Model A, small encoder) |
|---|---|---|---|
| Idea | one shared multilingual model | a frozen shared encoder with a small adapter per language, routed per text block | v4.1's recipe on a 4× smaller encoder |
| Encoder | XLM-R base, **all 277.5M parameters fine-tuned** | XLM-R base, **frozen** (as released by Meta) | Multilingual-MiniLM-L12-H384, **all 117.5M parameters fine-tuned** (21.5M transformer + 96M vocabulary embeddings) |
| Language-specific part | none | 11 bottleneck adapters (b = 64), **1.21M parameters each** (zh-Hans / zh-Hant share one) | none |
| Trained parameters | 277.5M | 13.3M (adapters + shared head) | 117.5M |
| Router | — | script rules + character n-gram classifier ([`src/router.py`](../src/router.py)) | — |
| Weights | `xlmr-base-pii-ml-v4.1.zip` (924 MB) | `xlmr-base-pii-adapters-v4.2.zip` (61 MB) + XLM-R base from the Hub | `minilm-pii-ml-v4.3.zip` (392 MB) |
| Use when | best accuracy, one model | per-language maintenance: a new language is one ~5 MB adapter, not a new 1.1 GB model | speed: 2.3× faster than v4.1 on GPU, 3× on CPU, faster than v3 |

**Why v4.** The English-only v3 scored 0.98 F1 in English but only 0.28–0.76 elsewhere
([`multilingual_zero_shot.md`](multilingual_zero_shot.md)). It missed most names, companies and
addresses written in a non-Latin script; for Thai it found none.

**Which to use:**
- **v4.1** for multilingual text when accuracy matters most. It is the most accurate on every
  multilingual benchmark.
- **v4.3** for multilingual text when speed or CPU deployment matters. It is within 0.3–1.3 points of
  v4.1 on the multilingual benchmarks, and faster than every other release including v3 (0.38 s vs
  v3's 0.60 s on GPU for a 100k-character document; 6.7 s vs 9.3 s on CPU). See [v4.3](#v43-multilingual-minilm).
- **v3.0** for English-only work. v4.1 is 1.5 points below v3 on the English test set and tags
  more look-alike codes as PII (see [Regressions](#regressions-and-limitations)).
- **v4.2** is the research answer to whether per-language adapters on a frozen shared encoder can
  replace a shared model:
  - **On text like its training sources, yes.** It is within 0.4–1.2 points of v4.1 on public data,
    mixed-language documents and real Korean financial documents, while training 4.8% of the
    parameters.
  - **On unseen financial document formats, no.** It drops from 0.873 to 0.690, and English drops
    from 0.910 to 0.821. See [Why v4.2 falls behind](#why-v42-falls-behind-on-financial-formats).

## Labels

As v3: `PERSON`, `BUSINESS`, `ADDRESS`, `DOB`, `ACCOUNT`, `PHONE`, `EMAIL`, `TIN`, BIO-tagged
(17 labels). The rules are the same:
- a bare place name is not an ADDRESS
- an ordinary date is not a DOB
- amounts, PINs, CVVs, SWIFT / IFSC / branch codes and OTPs are not PII
- national IDs and passports are excluded from scoring

Honorifics are not part of a name: 张伟先生 → PERSON 张伟; คุณสมชาย → PERSON สมชาย; 김민수 고객님 → PERSON 김민수.

### Why v4.2 falls behind on financial formats

On `ml_synth` (KYC forms, statements, transfer instructions) v4.2 loses most on three things:

| Gold entity (`ml_synth`, gold-language routing) | v4.1 | v4.2 |
|---|---|---|
| BUSINESS in ms / vi / ko | found 53–76% | **missed 86–96%** |
| ACCOUNT in ms / ja | ACCOUNT 60–75% | read as TIN / PHONE |
| ADDRESS in zh-Hans / ja / id / vi | found, boundaries often wrong (strict 0.23–0.57) | found, boundaries almost always wrong (strict 0.00–0.03) |

Gold-language and router scores are the same here, so routing is not the cause. Lenient F1 is
0.842 (v4.1: 0.946).

The likely cause is that format knowledge doesn't transfer between languages. Most of what
teaches *document format* in the training data is English: 74k documents including KYC forms,
statements and look-alike records.
- **v4.1 shares all its weights**, so that knowledge carries over to a Malay or Vietnamese form.
- **v4.2 keeps each language in its own 1.2M-parameter adapter on a frozen encoder.** The Malay
  adapter learns only from Malay data, which is mostly news-style NER and generic PII.

Capacity also matters: English, which has the most data, still drops from 0.910 to 0.821 on its
test set (BUSINESS 0.825 → 0.547).

The planned next step is **B′**: adapters on v4.1's fine-tuned encoder, which keeps the shared
cross-lingual knowledge. Larger adapters (b = 128) or unfreezing the top layers are alternatives.

### Language router (v4.2)

Document-level routing accuracy:
- `ml_synth`: 98–100% for every language.
- Kiii² test: 100%.
- `ml_real`: 94–99.5% for every language except English (84.6%) and Tagalog (93.8%). Wrongly
  routed English documents go mostly to Tagalog: AI4Privacy's English rows are full of romanised
  Asian names.

Effect on accuracy, v4.2 with the router vs the gold language:

| | `ml_real` | `ml_synth` | `ml_mixed` | Kiii² |
|---|---|---|---|---|
| router | 0.930 | 0.690 | 0.921 | 0.854 |
| gold language | 0.936 | 0.689 | 0.929 | 0.854 |

The router costs 0.6–0.8 points on real and mixed documents and nothing on the others. v4.2's gap
to v4.1 is **not** a routing problem.

### Latency (one 100,000-character English document, RTX 5060 Ti / 6 CPU threads)

| | v3 | **v4.1** | v4.2 | **v4.3** |
|---|---|---|---|---|
| GPU, median of 20 | 0.62 s | 0.87 s (1.4×) | 5.85 s (forward pass 0.79 s) ‡ | **0.38 s (0.6×)** |
| CPU, median of 3 | 9.5 s | 19.6 s (2.1×) | 27.3 s (forward pass 20.0 s) ‡ | **6.7 s (0.7×)** |
| Parameters (transformer layers) | 70.7M (22M) | 277.5M (86M) | 290.8M (86M + 13.3M) | 117.5M (21.5M) |

v4.3 was timed in a separate session against v3 (0.60 s / 9.3 s) and v4.1 (0.87 s / 19.8 s); the
ratios are from that session. MiniLM's BERT attention is cheaper per token than DeBERTa's
disentangled attention, which is why v4.3 is faster than v3 despite a similar transformer size.

‡ v4.2's forward pass costs the same as v4.1's. The extra time is in `predict()`: it runs a
separate inference for every routed text block, and the benchmark document is many short
documents joined by blank lines. Grouping all blocks of one language into a single batch would
remove most of this; that's a known issue in this release.

On GPU, 83–99% of v4.1's time is the encoder forward pass. 69% of XLM-R's parameters are its
250k-token embedding table, which costs memory but almost no compute. Speed follows the 86M
transformer parameters: 4× v3's 22M, but running 1.4–2.1× slower. Measured with
[`src/bench_latency.py`](../src/bench_latency.py).

**Generated data, and why.** It was used only where no public dataset exists:
- **Thai:** no public Thai PII data at all; ThaiNER has names and organisations only.
- **Arabic:** no public tax IDs, and few dates of birth.
- **Hindi:** no public Devanagari dates of birth, accounts or PAN numbers. AI4Privacy's Hindi
  entities are romanised.
- **Look-alike codes (all languages):** no public dataset labels SWIFT / branch codes, PIN, CVV,
  OTP, expiry dates or amounts as not-PII. The PII values in these records are real training
  spans; only the field labels and code values are generated.

**Rejected sources:**
- Meddies PII: medical.
- PhoNER-COVID19: medical.
- Maskara Indian PII: its "hi-IN" rows are Indian English.
- IndiaPII-Bench: evaluation-only by its terms.
- AI4Privacy PFI-400k (financial, 7 of our languages): gated, access still pending.

**Mapping and partial labels.**
- NER corpora label every place, so a bare LOC is loss-masked instead of taught as O.
- NER corpora have no number labels, so digit tokens outside their spans are loss-masked.
- SITR labels one PII type per row, so it is used positive-only.
- Known look-alikes are explicit O spans.
- Kiii² phrase spans are reduced: `생년월일은 1960년 6월 2일이며 만 66세` → DOB `1960년 6월 2일`, and
  titles are stripped from names (`박호 어머님` → `박호`).

**Composition.**
- Only Korean has real financial documents (48% of its spans).
- Thai is 85% generated, Arabic 52%, Hindi 37%.
- The other languages are 79–91% public general PII text.

## Training

| | v4.1 | v4.2 |
|---|---|---|
| Start | `xlm-roberta-base` | `xlm-roberta-base` (frozen) + zero-initialised adapters |
| Trained | everything | adapters + shared head |
| Learning rate | 2e-5 | 1e-4 |
| Epochs / batch / window | 3 / 32 / 384 tokens (stride 96) | same |
| Steps / time (RTX 5060 Ti) | 35,604 / 1 h 21 min | 35,604 / 2 h 17 min (gradients still pass through the frozen layers) |
| Checkpoint selection | macro-average F1 over the 12 languages of `ml_val` | same |
| Best validation macro-F1 (overall F1) | 0.946 (0.962) | 0.937 (0.953) |

Adapters (Houlsby / Pfeiffer output position, [`src/adapters.py`](../src/adapters.py)):
```
inside each of the 12 layers:  h = FFN output
  h = h + up(GELU(down(LayerNorm(h))))   # language adapter; up starts at zero
  out = LayerNorm(h + attention output)
```

Batches mix languages, and each example passes through its own language's adapter (the gold
language in training). The shared head never sees which adapter was used.

### Tokenization changes

These are stored in the model config and applied automatically by `PIIPredictor`.
- **`script_boundaries`.** v3 treated an unspaced run of CJK / Thai characters, and digits written
  next to them, as one word, so one prediction labelled the whole run.
  New models start a word at every CJK / kana / Thai token and wherever the script changes.
  v3 alone improves from 0.598 to 0.675 on `ml_real` with this.
- **Lone "▁" offset fix.** XLM-R's fast tokenizer gives the SentencePiece space before CJK / Thai /
  digits the offset of the *next* character. It is remapped, so it isn't read as the first
  character of an entity.

## Usage

```python
from predict import PIIPredictor           # run from src/
p = PIIPredictor("../outputs/xlmr-base-pii-ml-v4.1")
p.predict("尊敬的张伟先生：您的账户6222 0212 3456 7890 已更新。")
# [{'label': 'PERSON', 'text': '张伟', ...}, {'label': 'ACCOUNT', 'text': '6222 0212 3456 7890', ...}]

p = PIIPredictor("../outputs/xlmr-base-pii-adapters-v4.2")   # downloads xlm-roberta-base once
p.predict(text)                 # routed per blank-line block; spans carry "lang"
p.predict(text, lang="th")      # or force a language
```

## Regressions and limitations

- **English test set: 0.910 vs v3's 0.925.** ACCOUNT, DOB, PHONE and TIN each lose 4–13 points.
  English shares capacity with 11 other languages. **Use v3.0 for English-only work.**
- **Look-alike codes:** v4.1 tags 10.9% of the stress set's PIN / CVV / SWIFT / routing codes as
  PII (v3 6.6%), mostly as TIN / ADDRESS / PHONE. Despite the added look-alike records.
- **Slower:** 1.5× v3 on GPU, 2× on CPU.
- **Wealth-management formats** outside the sources' styles are the weakest part: addresses,
  company names and tax IDs in zh / ja / ko / vi / id (strict F1 0.23–0.81, lenient 0.89–0.94).
- **Hindi / Arabic / Thai** depend heavily on generated documents (37–85% of spans). Their test
  scores overstate real-world quality, and there is no public test set for Arabic or Thai.
- **`ml_real` is partly in-distribution.** It comes from AI4Privacy's validation split, and
  AI4Privacy's train split is training data. The score is optimistic.
- **Korean names** in `ml_real` are 0.59. Part of this is label noise in AI4Privacy's Korean rows
  (gold spans ending mid-word).
- **Same-sentence code-switching** isn't tested; `ml_mixed` switches language between blocks.
- Khmer, Burmese and Lao are not covered.
- **v4.3 specifically:**
